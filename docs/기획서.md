# PhotoAI Organizer 기획서

**AI 기반 사진 파일명 자동 생성 및 정리 프로그램** · 문서 버전 V1.3 (구현 결과 반영)

> 표기: **[변경]** 초안에서 바꾼 내용, **[추가]** 초안에 없던 내용, **[확인필요]** 결정이 필요한 항목

---

## 1. 개요

### 목표
사진의 EXIF 촬영일, GPS, AI 분석 결과로 사람이 알아볼 수 있는 파일명을 만들고, 폴더로 정리하는 Windows 프로그램. 수천~수만 장을 최소한의 조작으로 정리하는 것이 목표다.

### 예시
| | 파일명 |
|---|---|
| 변경 전 | `IMG_20210216_191725.jpg` |
| 변경 후 | `20210216_191725_연수구송도동_산책중.jpg` |

### 사용자 흐름
```
원본 폴더 선택 → [분석 시작] → 자동 파일명 생성 → 자동 정리 → 정리완료
```

## 2. 기본 원칙

1. **확인 가능한 정보만 쓴다.** 정보가 없으면 해당 항목을 파일명에서 뺀다.
   - 촬영일 없음 → 날짜 제외 / GPS 없음 → 장소 제외 / AI 실패 → 설명어 제외
2. **추정 금지.** 파일 생성일, 수정일, AI가 추정한 촬영일은 쓰지 않는다.
3. **실패한 파일은 원본 위치에 그대로 둔다.**
4. **[변경] 원본은 검증 후에만 제거한다.** 초안은 "이동 후 원본 제거"였으나, 복사 → 크기·해시 검증 → 원본 삭제 순서로 처리한다. 같은 드라이브면 이동(rename)으로 처리해도 된다. 중간에 중단돼도 원본이 사라지지 않게 하기 위함이다.

## 3. 플랫폼 및 배포

- V1: Windows 전용, 포터블 `PhotoAI.exe`. 추후 설치형 `PhotoAISetup.exe`.
- **[추가]** Ollama와 비전 모델(기본 gemma3:4b)(수 GB)은 exe에 포함할 수 없다. [분석 시작] 시 Ollama 연결과 모델 설치 여부를 검사한다(`ai.diagnose`).
  - **[변경]** 없으면 사용자 동의를 받아 자동 준비한다(`ai.prepare`): 공식 `OllamaSetup.exe` 다운로드 후 `/SILENT` 설치 → `ollama serve` 실행 → 모델 `pull`. 진행 상황은 상태줄·진행바에 표시한다. 대화상자에서 "아니요"를 고르면 "AI 미사용" 모드로 계속한다.
  - 원격 Ollama URL(localhost가 아님)은 자동 설치하지 않고 "AI 없이 계속" 여부만 묻는다.
  - 확인됨: 실제 Ollama 자동 설치(`/SILENT` 포함)와 모델 자동 다운로드, AI 설명어의 파일명 반영이 동작함을 확인했다.

## 4. 처리 파이프라인

```
원본 폴더 선택 → EXIF(촬영일·GPS) → 장소명 조회 → AI 분석(선택)
→ 파일명 생성 → 중복 검사 → 정리완료 폴더로 이동 → 원본 제거
```

- **[추가]** 하위 폴더 포함 여부를 옵션으로 둔다(기본 ON). 결과 폴더가 원본 폴더 안에 있으면 재스캔에서 제외한다.
- **[추가]** 지원 형식: JPG, PNG, WEBP, **HEIC**(아이폰, pillow-heif 사용). RAW는 V1 범위 밖이며 건드리지 않는다.
- **[확인필요] 동영상(MP4, MOV):** 메타정보로 사진과 같은 규칙의 파일명 생성이 가능하다. 아래 내용을 확인하고 포함 여부를 정한다.
  - 촬영일: 컨테이너의 `creation_time`(UTC)을 로컬 시간으로 변환해 사용한다. 값이 비었거나 1904-01-01이면 "촬영일 없음"으로 처리한다.
  - GPS: 아이폰(`com.apple.quicktime.location.ISO6709`)과 안드로이드(`©xyz`) 영상에는 위치가 들어 있는 경우가 많다. 없으면 장소 제외.
  - AI: 영상 중간 지점의 프레임 1장을 뽑아 같은 방식으로 분석한다.
  - 필요 도구: `ffprobe`/`ffmpeg`(exe에 포함하면 약 80MB 증가). 해시는 대용량이므로 청크 단위로 계산한다.
  - 주의: 편집·내보내기·메신저 전송을 거친 영상은 `creation_time`이 촬영일이 아니라 변환 시각인 경우가 있다. "추정 금지" 원칙상 의심스러운 값은 분류불가로 보낼 수 있다.

## 6. EXIF 정책

- 사용: `DateTimeOriginal`, GPS
- 촬영일 있음 → 정상 처리
- 촬영일 없음 → `정리완료/분류불가`로 이동 (파일명 규칙은 10장 참고)
- 날짜 형식은 `YYYYMMDD_HHMMSS`.

## 7. GPS·장소명 정책

- GPS 있음 → 카카오 로컬 API로 장소명 조회. GPS 없음 → 장소 제외.
- **캐시:** SQLite에 `좌표 → 장소명`을 저장하고 이미 조회한 좌표는 API를 호출하지 않는다.
  - **[추가]** **[변경]** 캐시 키는 좌표를 0.002도(약 200m) 격자로 묶어 인접 좌표를 같은 키로 쓰고, 키에는 격자 중심 좌표(예: `37.500,126.600`)를 저장한다(기존 10m 단위는 적중률이 낮았고, 500m는 동 경계 오류 위험이 커서 200m로 정함). 동 경계 근처 사진은 이웃 동 이름이 붙을 수 있다. 이전 방식의 캐시 항목은 키 형식이 달라 재사용되지 않는다.
- 장소명은 최대 10자.
- **[확정]** 장소명은 POI(건물·공원 이름)가 아니라 **주소명**을 쓴다. 카카오 좌표→행정구역 API(`coord2regioncode`)를 사용하고, `구/시` + `동/읍/면`을 이어 붙인다. 시·도 이름은 뺀다.
  - 예: `연수구송도동`, `강남구역삼동`, `제주시구좌읍`
  - 10자를 넘으면 `동/읍/면`을 우선 남기고 앞부분을 줄인다. 같은 동 이름이 여러 곳에 있어도 파일명 용도로는 허용한다.
- **[확정]** 카카오 REST API 키 하나만 쓴다. JavaScript 키와 네이티브 앱 키는 이 API에서 401로 거부되므로 쓰지 않는다.
- **[추가] 사전 조건:** 카카오 개발자 콘솔에서 해당 앱의 **카카오맵(로컬) 서비스를 "사용 설정 ON"** 해야 한다. 꺼져 있으면 403 `disabled OPEN_MAP_AND_LOCAL service`가 돌아오고 장소명은 모두 생략된다(2026-11-03 확인). 서비스를 켠 뒤 정상 조회와 파일명 반영을 확인했다. HTTP 오류의 응답 본문은 `logs/error.log`에 남긴다.
- **[추가]** 조회 실패(네트워크 오류, 일일 쿼터 초과)는 "GPS 없음"과 구분해 장소만 생략하고 처리를 계속한다. 이 결과는 캐시하지 않는다.
- 좌표가 외부(카카오)로 전송된다는 점을 설정 화면에 명시한다.

## 8. AI 분석 정책

- 사용: Ollama + Gemma 3 4B(기본값, 설정에서 변경 가능; 이전 기본값은 Qwen2.5-VL). 분석 항목은 분위기, 행동, 사진 특징 → 결과는 짧은 한 단어(설명어)로 요약. 예: 산책중, 가족사진, 일몰풍경, 반려견, 커피사진.
- AI 미사용 → 메타정보(날짜·장소)만으로 이름 생성. 예: `20210216_191725_연수구송도동.jpg`
- AI 실패(타임아웃, 빈 응답, 규칙 위반) → 설명어 없이 진행. **[추가]** 1회 재시도 후 실패 처리.
- **[추가]** AI 출력은 9장 규칙으로 후처리하고 규칙을 만족하지 못하면 실패로 본다.
- 참고: 설명어는 AI의 해석이므로 "확인 가능한 정보만" 원칙의 예외다. 선택 기능이고 사용자가 끌 수 있으므로 허용한다.

## 9. 설명어(초안의 "상태명") 규칙

- 최대 10자, 공백 금지, 특수문자 금지(Windows 금지문자 `\ / : * ? " < > |` 포함).
- **[변경]** 용어를 "상태명"에서 **설명어**로 바꾼다. (분위기·행동·특징을 모두 포함하므로)

## 10. 파일명 규칙

| 촬영일 | GPS | AI | 파일명 | 저장 위치 |
|---|---|---|---|---|
| O | O | O | `날짜_장소_설명어.jpg` | 정리완료 |
| O | O | X | `날짜_장소.jpg` | 정리완료 |
| O | X | O | `날짜_설명어.jpg` | 정리완료 |
| O | X | X | `날짜.jpg` | 정리완료 |
| X | - | O | `원본파일명_설명어.jpg` | 정리완료/분류불가 |
| X | - | X | `원본파일명.jpg` | 정리완료/분류불가 |

- **[확인필요]** 현재 구현은 촬영일이 없으면 AI·장소 조회를 하지 않고 위 5행도 `원본파일명.jpg`로 둔다(설명어를 붙이지 않음). 5행대로 구현할지 정해야 한다.

- 예: `20210216_191725_연수구송도동_산책중.jpg`, `KakaoTalk_20240705_015802579_가족사진.jpg`
- **[추가]** 확장자는 소문자로 통일. 전체 경로가 Windows 260자를 넘으면 설명어 → 장소 순으로 줄인다.
- **[추가]** 촬영일이 없는 사진은 `원본파일명`에 이미 설명어가 붙어 있는 경우(재실행)를 중복으로 붙이지 않는다.

## 11. 중복 파일 처리

**동일 파일 검사** 체크박스 (기본 ON). 같은 이름이 생성될 때만 비교한다.

| 설정 | 이름 동일 + 해시 동일 | 이름 동일 + 해시 다름 |
|---|---|---|
| OFF | `파일_001.jpg`, `파일_002.jpg` … | 같음 |
| ON | `정리완료/중복파일`로 이동 | `파일_001.jpg`, `파일_002.jpg` … |

- **[추가]** 해시는 SHA-256(파일 내용). 지각적 해시(ImageHash)는 "비슷한 사진" 탐지용이므로 V6에서 쓴다.
- **[추가]** 연사처럼 촬영일(초 단위)이 같고 내용이 다른 사진은 위 규칙으로 `_001`이 붙는다.

## 13-1. 로그 파일 **[추가]**

개발 단계의 문제 추적용. 실행 폴더(exe 옆 또는 프로젝트 루트) 아래 `logs/`에 저장한다(`.gitignore` 대상).

## 16. 개발 범위

**이번 개발은 V1까지만 한다. V2 이후(다국어, 날짜별 폴더, 다중 AI, 클라우드 연동, 얼굴 인식, 사진 품질 분석 등)는 범위 밖이다.**

- **[확정] 동기화 방침:** 데이터(GPS 캐시, 통계, 이력)는 우선 개인 PC의 SQLite에만 저장한다. 개발자 서버가 준비되면 그때 동기화한다.
  - V1에서는 서버 기능을 만들지 않는다. 다만 나중에 동기화할 수 있도록 테이블마다 `id`(UUID), `updated_at`, `synced`(0/1) 컬럼을 둔다. **[추가]**
- V1 개발 순서 제안: ① 파일명 생성·이동 코어(AI/GPS 없이) → ② 중복 처리·이력·되돌리기 → ③ 카카오 주소명 조회·캐시 → ④ Ollama 연동 → ⑤ GUI·통계 → ⑥ exe 빌드.
